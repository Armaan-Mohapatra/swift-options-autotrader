## 2. Functional scope and owner rules

Preserve the approved strategy as deterministic rules, not LLM-generated orders. Scope is single-leg long calls/puts in the pinned dedicated MCP account; no short options, spreads, exercise, crypto, equities, account transfers or trading in another account. Out-of-scope or ambiguous alerts are ignored with a reason. Owner must confirm supported underlying classes; do not extend an equity-only pilot to index options without evidence of contract rules and approval.

| Alert | Required behavior |
|---|---|
| Fresh authenticated initial options callout | One validated entry proposal; preserve exact ticket limit |
| LOTTO | Same eligibility checks; no special leverage or increased size |
| ADDING MORE / averaging down | Ignore; no additional purchases |
| NEW AVG / revised average | Informational metadata; never substitute for actual fill-cost basis |
| SOLD HALF / partial sale / RUNNERS OUT / ALL OUT | Exit the entire matching Swift-owned remaining position, when validly linked and authorized; never unrelated holdings |
| Non-options, malformed, unlinked or unsupported message | Record reason, no trade |
| Historical/recovered entry, duplicate or superseded revision | No newly initiated order |
| Exit received before fill | Persist exit intent; reconcile pending buy/cancel/fill before attempting a close; no naked sell |

Single alert price is exact. Existing parser computes the exact midpoint for price ranges; preserve this existing behavior only if the owner confirms it remains desired. Never round silently to a valid tick, infer an absent expiration year when multiple candidates match, or chase a missed limit. Original candidate has 120-second fresh-entry eligibility, 60-minute unfilled-entry cancellation review, regular-session GFD limits. Preserve or get explicit owner approval for changes. Exit pricing and retry policy should be taken from existing reviewed code and confirmed; do not guess a replacement policy. Do not replay stale entries on restart. Recovered followups only if linked to known owned trades and explicitly eligible under recovery rules.

Existing code ceilings: one contract per initial alert, $999 premium per trade, $9,999 aggregate exposure, $655 daily gross realized loss stop. These are upper ceilings, not a proposed capital allocation or guarantees. The paper pilot separately chose three active positions; this is not an approved live concurrency cap. Owner must explicitly select lower effective live caps consistent with available capital, position count, daily order budget, expiry policy and mandate duration. Include working and unknown orders, fees and externally held/reserved exposure in account checks; keep reserve calculations conservative. Use Decimal and verified multiplier/units, not floats or implicit defaults. New-entry loss limits can be breached by gaps, existing holdings or slippage; do not represent a stop as a guaranteed loss cap. Define separate entry, risk-reducing exit and cancel controls so a cap does not accidentally strand risk, while still respecting authorization and broker requirements.

## 5. Authorization and release modes

Separate READ_ONLY, PAPER, SUPERVISED_LIVE and UNATTENDED_LIVE modes. Default receive-only; paper/read-only must have no broker write capability, not just a UI flag. Supervised execution is a separately approved local action. Unattended mode must require owner-issued, expiring, account/channel/release/config-bound authorization and independently verified broker eligibility. A disabled account approval setting by itself is insufficient. Local authorization must never approve a broker-required human confirmation; notify the owner and do not create a second submission. Avoid creating pending approval requests as a side effect of unattended checks until their lifecycle is documented. If approval required, unsupported or unknown, pause. Keep revocation, stop marker, broker-side disconnect and conservative failure policy. No automatic mandate renewal. Existing mandate is a local hash integrity check, not protection from an attacker with local write access; use restrictive ACLs and stronger authenticated configuration if needed. Existing code limits mandate validity to 14 days and caps daily orders; do not raise bounds or remove expiry without explicit reviewed owner requirements. Bind the authorized limits to the exact release and risk config, including exit/cancel scope. Review how open positions are handled at expiration and revocation; no unapproved fallback actions.

## 6. Execution state and correctness requirements

Design a single serialized execution owner that consumes canonical validated tickets from the receiver database rather than duplicating the Telegram listener. The current companion launches its own `telegram-listen` child and takes the existing service lock, so it cannot simply be started beside the receive-only supervisor. Either deliberately refactor to a read-only DB consumer with a *separate* exclusive account-execution lock, or implement a controlled handoff after stopping the receiver and disabling its task. Never delete a live lock file to bypass ownership. Avoid concurrent OAuth refresh races; coordinate token refresh/ownership using supported local storage.

Use durable state transitions: received/validated, blocked or reviewed, owner/broker authorized, intent persisted, submitted/unknown or acknowledged, working/filled/cancel pending/terminal, exit required/closed. Define transitions for broker pending-approval, rejection, expiration, transport failure, cancel/fill races and restart. Normalize only documented states. Before any write, durably record the logical action, account/contract/source lineage, authorized parameters, request digest and exposure reservation. Use broker-documented client correlation/idempotency only when supported; a local UUID is not a broker guarantee. Persist broker-assigned order IDs and verified executions separately. After a lost acknowledgment, do not retry, clear the journal or adopt a similar order. Freeze new submissions and reconcile against exact broker evidence with operator involvement if identity remains ambiguous. A partial fill record must agree with verified leg executions and broker quantities. Close only confirmed owned inventory and reconcile pending sells first. External/manual holdings or same-contract activity must not be adopted as bot lots or accidentally sold. Durable journal migrations must validate, back up, and be reversible without dropping attempts or records. Reconcile complete paginated order and position snapshots at startup and after disconnect; unknown state means pause, not reset.

Maintain entry freshness, market sessions/holidays (New York timezone), source eligibility, quote identity/freshness, verified contract multiplier/tick, account and position ownership, buying power, exposure, risk and authorization checks at final decision time. Limit order is not a guaranteed fill. Do not substitute market order, increase price, or sell in response to text unlinked to an owned entry. Maintain a local audit trail explaining every blocked or accepted ticket without secrets.
