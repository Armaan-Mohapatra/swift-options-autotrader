# Final acceptance criteria (not executable production instructions)

No changes to the owner laptop during intermediate development. No real-money startup command is supplied. Restore existing receive-only and paper operation only in a later consolidated supervised Windows acceptance stage after review of actual task actions, exact installed runtime, owner identity, stops, and current logs. Do not blindly run the archived scripts; the receiver recovery is still native-untested and expects original paper package bytes, not the review overlay.

## Offline / native acceptance boundary

A future production installer must independently verify a complete immutable candidate and locked dependencies, preserve existing user-managed state and secrets, check exclusive process ownership, retain persistent stops, validate status against fresh heartbeats AND matching processes, and use a transactional state-compatible promotion with safe rollback. It must be tested on Windows, including PowerShell syntax, DPAPI under actual user/machine, Task Scheduler actions and logon/restart behavior. The supplied mock pointer rehearsal is not an implementation of that installer. No production rollback is attempted here. For a future real rollback, freeze dispatch, reconcile outstanding orders through the broker, preserve all journals including newer entries and SQLite WAL-consistent backups, and validate schema compatibility before selecting previous reviewed source. Never restore an old account transaction journal over a current one. An emergency stop does not cancel orders or close positions; review them independently with the broker.

## External verification

Observe a genuinely new Telegram source revision and current market quotes with timestamp, supported instrument, position ownership and verified price units. Observe paper entry and exit lifecycle and restart without duplication. Establish actual documented provider approval semantics and order acknowledgment vs terminal fill/cancel outcomes through independently verified read-only evidence or supported provider test environment. Any real transaction should be separately owner-approved and handled through the authorized brokerage interface; no trade should be made merely to satisfy tests. Do not treat a local JSON file or structural fields as proof of broker permission. Any future release requires independent review, native operational validation, actual provider-supported certification and owner-confirmed risk limits. No such certification is claimed here.
